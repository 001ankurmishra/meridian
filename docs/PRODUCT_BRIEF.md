# Product Brief — Project Meridian

**Read every coding session?** Conditionally (product/feature work — yes; pure infra/refactor — optional)

---

## 1. What Meridian Is

Project Meridian is an **evidence-backed agentic AML (Anti-Money Laundering) investigation copilot**. It receives an AML alert generated by an upstream transaction-monitoring/fraud-detection system and performs a structured, multi-step investigation across customer information, transaction history, entity/transaction relationships, risk signals, sanctions/watchlist data, and relevant policy documents.

Meridian answers: *"Why is this activity suspicious, what evidence supports the suspicion, what policy applies, and what should the human investigator review next?"*

It produces an **evidence-linked investigation report and recommendation** for a human AML analyst. It does not itself accuse, decide, freeze, or file — see `docs/PRODUCT_PRINCIPLES.md` and `docs/AI_SAFETY_AND_GUARDRAILS.md`.

**Positioning:** an evidence-backed agentic investigation system for AML analysts — not a chatbot, and not a fraud/AML "black box" classifier.

---

## 2. Problem Statement

Transaction-monitoring systems (rules, thresholds, ML risk scores, watchlists, pattern detectors) are effective at generating *alerts*, but an alert is only the start of an investigation. Analysts must manually review customer history, transaction patterns, counterparties, relationship graphs, sanctions exposure, and applicable policy, then write a case narrative — a large, repetitive analytical workload. Meridian automates the repetitive evidence-gathering and drafting work while keeping the human accountable for the final determination.

---

## 3. Target Users

**Primary:** AML analysts, financial crime investigators, compliance analysts, transaction-monitoring teams, risk analysts.
**Secondary:** compliance managers, fraud investigation teams, internal audit, financial crime operations.

---

## 4. Core Workflow

```
AML Alert
  → Investigation Orchestrator
    → Collect Evidence (structured + graph + policy)
    → Analyze Transactions
    → Analyze Customer Behavior
    → Analyze Entity/Transaction Graph
    → Check Sanctions / Watchlist Screening
    → Retrieve Relevant Policy (RAG)
    → Cross-check Evidence
    → Generate Findings (Fact → Signal → Interpretation → Recommendation)
    → Generate Evidence-Backed Report
  → Human AML Analyst
    → Approve / Reject / Request More Investigation / Escalate
```

The Orchestrator decides which agents/tools a given case actually needs — it does not blindly run every step for every alert (see `docs/ARCHITECTURE.md`).

## 5. Worked Example (Reference Scenario)

- Customer: synthetic profile "Rahul Sharma" (synthetic data — see `docs/DATA_AND_DATASET_STRATEGY.md`)
- Alert: ₹9,80,000 transferred to a newly created beneficiary
- Alert reasons: unusually large transaction, new beneficiary, multiple incoming transfers shortly before, rapid fund movement, deviation from historical behavior
- Historical average monthly transfer: ₹60,000 → current transaction ≈16× that average
- Graph pattern: Customer A → ₹5,00,000 → Account B → ₹4,50,000 → Account C, with additional connections between B, C, and other accounts

This scenario is used consistently across `docs/FEATURES.md`, `docs/EVALUATION.md`, and the synthetic fixture data in `docs/TESTING.md` / `docs/DATA_AND_DATASET_STRATEGY.md`, so that architecture, tests, and demo narrative stay aligned.

---

## 6. Scope Boundaries

**In scope:** evidence collection and synthesis, transaction anomaly/risk signals, graph-based entity analysis, policy retrieval (RAG), structured (SQL) financial analysis, evidence-linked report generation, human review/approval workflow, full audit trail.

**Explicitly out of scope for Meridian as a system:** autonomous account actions, autonomous regulatory filing, real production bank integration, real customer PII, real-time production-scale streaming (Kafka etc.) unless a phase explicitly justifies it (see `docs/ROADMAP.md` and ADR-0001).

---

## 7. Success Definition

Meridian is successful as a portfolio/engineering project if it demonstrably: (1) produces investigation reports where every material finding traces to real evidence in the synthetic dataset, (2) correctly separates structured retrieval from RAG, (3) enforces human-in-the-loop on all high-impact outputs, (4) is measurably evaluated (not just narratively described) per `docs/EVALUATION.md`, and (5) remains auditable end-to-end per `docs/OBSERVABILITY_AND_AUDIT.md`.

It is **not** successful merely because "the AI produces plausible-looking reports." Plausibility without evidence-traceability is treated as a defect, not a feature.
